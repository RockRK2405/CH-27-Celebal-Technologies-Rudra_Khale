The test set is future dates; every feature used for test predictions must be
knowable at the prediction cutoff (2015-06-19).

## TEST LEAKAGE CHECK: PASS

## What each check proves

1. **Column source.** No feature is the raw same-day `OrderVolume` or
   `AppSessions`. `AppSessions` is train-only (absent from test), so its
   contemporaneous value can never be used; only *historical* per-hub averages
   (known at the cutoff) appear.

2. **Lag horizon.** The forecast block is 42 days, so any target lag must be
   ≥ 42 days — otherwise the last block days would require an unobserved value.
   All lags used are `{42, 49, 56, 63, 364, 371}`. This makes validation and
   test have identical feature availability.

3. **Lag values.** `lag_42` for a target row exactly equals the historical
   `OrderVolume` at `date − 42` (500 random rows checked), confirming the
   date-shift merge references the correct past row and nothing later.

4. **Perturbation test (the decisive one).** We corrupt *every* `OrderVolume`
   at `Date > cutoff` (all future rows, including the target rows themselves)
   with random values and rebuild features. The feature matrix is **byte-for-byte
   identical** to the original. If any feature secretly read a present/future
   target, the matrix would change and this test would FAIL. It does not.

## Per-feature-group reasoning

| Group | Uses future target? | Why safe |
|---|---|---|
| Calendar (dow, month, cyclic, …) | No | pure function of the forecast date |
| Target lags (≥42) & `lag_42_63_mean` | No | reference `Date−k`, `k ≥ 42`, all ≤ cutoff |
| Hub/hub-weekday/hub-promo aggregates | No | computed from `history` (`Date ≤ cutoff`) only |
| Recent means / trend / last value | No | windows end at the cutoff |
| Historical AppSessions aggregates | No | past averages from `history ≤ cutoff`; same-day value never used |
| Metadata (format, tier, competitor/loyalty tenure) | No | static anchors + the (knowable) forecast date |
| Operational flags (IsOpen, PromoActive, holidays) | No | provided in the test file (planned/calendar) |

## Construction guarantee
Training examples are generated by `make_supervised`, which calls the **same**
`build_features(history, targets, cutoff)` used at inference. Because the audited
function is the single code path for both training and serving, a passing audit
covers the test-time predictions too.
